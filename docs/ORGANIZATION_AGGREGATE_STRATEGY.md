# Organization Aggregates Strategy

**Status:** Strategy, not started · Revised August 15, 2026

## The ask

Working with Estée Lauder means people in New York offices and people at a plant in Japan.

1. Pull everything from interactions with **anyone related to the company**, across sites and org
   units — and keep that history **even after a person moves on**, because it is still your
   history with the organization.
2. See **money spent at that organization** during the relationship, in the same view.
3. Do it **without adding primitives.** It is all interactions; the meaning comes from how they
   are filtered.

That last point is the correct frame, and it is already true in the data.

## What the data says

| | |
| --- | --- |
| Interactions | 7,397 |
| …`financial` | **5,565** (75%) |
| …`calendar` | 1,726 |
| …message / email / meeting | ~106 |
| Interactions carrying an organization | **0 — the column does not exist** |
| Financial interactions that can reach a Group today | **159 of 5,565 (2.9%)** |
| People | 7,376 — **4** with a `company` value |
| `PersonGroup` membership edges | **2** |
| Groups | 612, of which **611** are merchant brands auto-generated by the spend pipeline |

Meetings, emails, calendar events and purchases are already the same shape. Nothing needs to be
unified — it already is. **The only thing missing is that no interaction knows which organization
it belongs to.**

That single absence is what breaks all three requirements at once.

## The core move: one column, stamped at write time

Add a nullable, indexed `groupId` to `Interaction`.

That is the whole design. Everything below is consequence.

### Why stamped, not inferred

My first version of this proposed deriving the organization at query time by joining through
`PersonGroup` membership windows — "who did this person work for when this happened?" That is
wrong, for three reasons:

- **It depends on data that does not exist.** Two membership edges in the entire database, and
  no reason to believe start/end dates would be filled in reliably even once people start using
  it. A query that infers from missing dates returns nothing.
- **It rewrites history.** Edit a membership date and past aggregates silently change. Your record
  of who you talked to in 2022 should not move because someone corrected an end date in 2026.
- **It cannot express spend at all.** A purchase has no person to infer from, which is exactly why
  97% of financial interactions can reach no organization today.

Recording the organization **when the interaction happens** makes it a durable historical fact
rather than a derivation. The person leaves, changes jobs, gets merged or deleted — the
interaction still says Estée Lauder, because it was.

This is what makes requirement 1 work properly, and it is a straight consequence of taking "it's
all interactions" seriously: if the meaning is in the filtering, the dimension you filter on has
to be on the row.

### What it gives you

"Everything with Estée Lauder" collapses to an indexed filter over one table:

```sql
SELECT * FROM Interaction WHERE groupId = :el   -- meetings, emails, calls AND spend
```

Spend is not a separate question. `SUM(amount) WHERE groupId = :el AND type='financial'` answers
"what did I spend with them", over the same rows, with no second system.

`PersonGroup` still matters — it answers *who* you know there and is how you'd populate `groupId`
for new interactions — but it is no longer load-bearing for the history.

## How `groupId` gets filled

Three paths, in descending order of value:

1. **Financial → merchant resolution.** All 5,565 financial interactions carry a summary naming
   the merchant, and 611 merchant Groups already exist. `scripts/era/resolve-merchant-places.ts`
   already does merchant → Place; the same pattern gives merchant → Group and lights up the 97%
   that currently reach nothing.
2. **Calendar → attendee email domain.** 1,726 calendar interactions, and a domain is a strong
   organization signal. This is the cheapest way to backfill professional history.
3. **Explicit** — the assistant, or the person's current membership at the time of writing.

None of these need to be perfect. `groupId` is nullable; an unattributed interaction is exactly
what you have today.

## Where the non-interaction information goes

You were right that this should not add primitives. It also should not pretend everything is an
interaction — a market cap is not something that happened.

| Shape | Example | Home | Cost |
| --- | --- | --- | --- |
| Something happened with the org | meeting, email, purchase, received their investor deck | **Interaction** with `groupId` | the one column |
| A fact about the org, over time | market cap, headcount, revenue | **`State` on the Group** | **nothing — already polymorphic and dated** |
| Narrative research | earnings-call takeaways, "the Japan plant is being retooled" | **`Note`** with a nullable `groupId` | one column |

Receiving an investor deck genuinely *is* an interaction with the organization — no person needed,
which is another thing the `groupId` column unlocks.

I previously proposed a `GroupNote` join table and a `CompanyProfile` extension. Both are dropped:
a nullable `Note.groupId` does the same job for one column, and `State` already holds typed, dated
values against any entity including Group, so ticker and market cap need no new structure.

One caution on `Note`: it already has a `groups` relation, but that is the reverse of
`Group.sourceNoteId` and means *"this Group was derived from this Note."* A new `groupId` meaning
*"this Note is about this Group"* is a different edge and should be named and documented as such,
not folded into the existing one.

## Merchant groups and relationship groups are the same groups

I previously argued for a separate group type so curated companies would not mix with the 611
auto-generated merchant records. Given what you want, that was wrong — **one Group per real-world
organization is the point.** If Estée Lauder is both somewhere you spend money and someone you
work with, one Group is what makes those two facts meet.

The distinction you actually want is **derived, not declared**: an organization is a relationship
when it has people, notes, or non-financial interactions attached. Uber Eats will never accumulate
those and will simply never appear in a relationship view. No enum value required — which is the
same instinct as filtering interactions rather than typing them.

## Phasing

1. **`Interaction.groupId`** — nullable, indexed, additive. Nothing else matters until this exists.
2. **Merchant → Group resolution** for financial interactions, following the existing
   merchant → Place resolver. Biggest single unlock: 5,400 interactions currently attributable to
   nothing.
3. **Calendar attendee-domain → Group** backfill for professional history.
4. **`Note.groupId`** for research, and start recording company facts as `State` on the Group
   (no schema change needed for the latter).
5. **Company dossier surface** — one query, plus an assistant tool over it.
6. **Assistant write tools** (`create_group`, `add_person_to_group`) so membership gets recorded
   as a by-product of conversation rather than as data entry.

## Open questions

1. **Should `groupId` ever be corrected retroactively?** Stamping makes history immutable, which
   is the point — but a mis-resolved merchant will want fixing. Suggest corrections are allowed but
   recorded as GraphEvents, so the amendment is itself part of the history.
2. **What about a person who works with you across two employers?** Their EL-era interactions stay
   with EL and their new ones attach elsewhere, which is correct — but a person-centric view should
   probably show both, clearly labelled by era.
3. **One `groupId`, or several?** A meeting can involve two organizations. A single column is
   right until you have a real example; a join table is the escape hatch if you do.
4. **How aggressive should merchant → Group resolution be?** Wrong attribution is worse than none,
   since it silently inflates "what I spent with them". The Places importer's confidence tiering is
   the precedent to follow.
